## Review Boundary And Threat Model

Scriveno is a local CLI and package, not a hosted web service. The reviewed trust boundaries were local filesystem inputs, output and backup paths, archive members, optional executables resolved from `PATH`, the opt-in watermarks-remover HTTP client, environment-backed provider credentials, npm package creation and publication, Git tags, and GitHub Actions. There are no inbound application accounts, sessions, tenants, administrative endpoints, database queries, CORS settings, cloud roles, webhooks, or server-side authorization objects in this product form.

Named adversaries considered:

- A malicious file or archive supplied for audit or cleaning.
- A local filesystem race attempting to redirect a read or write.
- A malicious or compromised optional provider attempting redirects, malformed replies, oversized replies, secret reflection, or protected-content changes.
- A compromised CI action tag or npm publishing identity attempting package substitution.
- An abnormal process termination during multi-file in-place publication.

### A10 process-termination fault injection

Procedure:

1. In an isolated temporary directory, create `first.txt` as `A U+200B B` and `second.txt` as `C U+200B D`.
2. Start a child Node process that monkeypatches `fs.renameSync`, delegates the rename, and calls `process.exit(93)` immediately after the first staged temporary file is renamed onto either source.
3. Call `cleanTargets([first, second], { apply: true, inPlace: true, confirmInPlace: true })` inside that child.
4. After exit, inspect both sources, backups, and temporary siblings.

Observed result:

```json
{
  "childExit": 93,
  "first": "AB",
  "second": "C U+200B D",
  "backupCount": 2,
  "temporaryFileCount": 1,
  "partialPublication": true
}
```

Both original-byte backups survived, so the probe did not show data loss. It did show an interrupted batch with mixed publication state and no automatic restart recovery.

## Findings

### [MEDIUM-001] CI dependencies use mutable tags and implicit token permissions

- **Category**: OWASP A03:2025 Software Supply Chain Failures
- **Location**: `.github/workflows/ci.yml:1`, `.github/workflows/ci.yml:29`, `.github/workflows/ci.yml:32`
- **Description**: CI resolves `actions/checkout@v4` and `actions/setup-node@v4` through mutable major-version tags. The workflow also omits an explicit least-privilege `permissions:` block and does not explicitly disable checkout credential persistence. Actual token capability therefore depends on repository defaults.
- **Impact**: Compromise or unexpected movement of a referenced action tag can execute different code in CI, influence release-gate results, and access whatever `GITHUB_TOKEN` permissions the repository default grants. This workflow does not publish npm directly, which limits immediate package-release impact.
- **Reproduction**: Run `rg -n "uses:" .github/workflows` and `rg -n "^permissions:|persist-credentials" .github/workflows`.
- **Observed Result**: The only action refs are `actions/checkout@v4` and `actions/setup-node@v4`; no explicit permissions or checkout credential-persistence setting is present.
- **Evidence**: `.github/workflows/ci.yml:1-37`; manual probe at 2026-08-17T19:55:46Z.
- **Reviewed At**: 2026-08-17T19:55:46Z
- **Owner**: Scriveno release maintainer
- **Deadline**: 2026-08-31
- **Remediation Options**:
  - **Option A**: Pin both actions to reviewed full commit SHAs, add `permissions: { contents: read }`, and set checkout `persist-credentials: false`. Estimated: 1 hour.
  - **Option B**: Add an automated policy test that rejects non-SHA action refs and missing least-privilege permissions, then pin the current workflow. Estimated: 3 hours.
- **Status**: Open

### [MEDIUM-002] Reproducible package bytes are not bound to a signed release identity

- **Category**: OWASP A03:2025 Software Supply Chain Failures
- **Location**: `docs/release-checklist.md:65`, `docs/release-checklist.md:82`, `scripts/check-pack-reproducibility.js:75-140`
- **Description**: The release checks prove repeatable package bytes and npm supplies a registry integrity digest, but the source commit and release tag are unsigned and the local `npm publish` path produces no npm trusted-publishing provenance attestation. A digest proves equality only after a trusted party distributes the expected digest; it does not identify the publisher or bind the tarball to the reviewed commit.
- **Impact**: A compromised npm publishing credential or release workstation could publish substituted bytes under the valid package name without a consumer-verifiable link to the reviewed GitHub source revision.
- **Reproduction**: Run `npm run pack:repro`, `git verify-commit cbec5cf`, and `git verify-tag v3.7.0`; inspect the release checklist for provenance or signature steps.
- **Observed Result**: Pack reproducibility passed with SHA-256 `f7885075d59af0d9d8d8af98754610795dc3e3a3acc51ef2dbdf61a6a0cf88dc`. Commit and prior tag signature verification each exited `1`. The documented release path uses local `npm publish --access public` and records no attestation step.
- **Evidence**: Build ledger command `npm run release:check`; manual pack and signature probes at 2026-08-17T19:55:46Z.
- **Reviewed At**: 2026-08-17T19:55:46Z
- **Owner**: Scriveno release maintainer
- **Deadline**: 2026-08-31
- **Remediation Options**:
  - **Option A**: Sign the release commit and annotated tag, publish the tarball SHA-256 in the GitHub release, and verify all three before `npm publish`. Estimated: 3 hours plus key setup.
  - **Option B**: Move publishing to npm trusted publishing with GitHub OIDC provenance, environment protection, immutable action SHAs, and same-artifact promotion from the checked tarball. Estimated: 1 to 2 days.
- **Status**: Open

### [MEDIUM-003] Abrupt termination can leave an in-place batch partially published

- **Category**: OWASP A10:2025 Mishandling of Exceptional Conditions
- **Location**: `lib/provenance-clean.js:1263-1355`, `docs/provenance-hygiene.md:49`
- **Description**: The in-process transaction catches ordinary commit failures and rolls them back, but it has no durable journal or startup reconciliation. A process kill, host crash, or power loss after one rename but before the next rename bypasses the catch path.
- **Impact**: A confirmed multi-file in-place cleaning operation can return after restart with a mixture of cleaned and original files. Original-byte backups survive, so recovery is possible, but no report identifies the interrupted transaction and downstream tooling may consume the mixed state before manual inspection.
- **Reproduction**: In an isolated temporary directory, create two marked files. In a child process, wrap `fs.renameSync` so it performs the first staged rename and immediately exits `93`, then call `cleanTargets` with `apply`, `inPlace`, and `confirmInPlace` all true. Inspect sources, backups, and temporary siblings after the child exits.
- **Observed Result**: `first.txt` contained cleaned `AB`; `second.txt` retained its original marked bytes; two backups remained; one staged temporary remained; the child emitted no recovery report.
- **Evidence**: Manual termination probe at 2026-08-17T19:55:46Z; synchronous rollback tests passed in `test/provenance-clean.test.js`, which confirms the gap is specific to termination outside JavaScript error handling.
- **Reviewed At**: 2026-08-17T19:55:46Z
- **Owner**: Scriveno provenance maintainer
- **Deadline**: 2026-08-31
- **Remediation Options**:
  - **Option A**: Write and fsync a transaction journal before the first in-place rename, update it after every rename, and reconcile or report unfinished transactions on the next provenance-clean start. Estimated: 1 to 2 days.
  - **Option B**: Disallow multi-file in-place mode and require verified cleaned-copy publication followed by a separate explicit promotion step. Estimated: 4 to 6 hours.
- **Status**: Open
